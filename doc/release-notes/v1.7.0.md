# v1.7.0

## 403 不再算作证据

被动健康反馈此前是"上游响应头一到就记成功"。这条规则有个副作用：上游返回
403 时，节点会被记为成功，`FailureCount` 清零、熔断解除——一个**用不了的出口
被洗回调度池**。

但 403 也不能记失败。同一个状态码对应两种完全不同的原因：

- `abusive traffic from this IP address` —— 这个出口被封，是节点问题
- `can only be used from within OpenCode` —— 请求特征不对，是配置问题

后者与节点无关，拿它判节点失败是冤枉好人。而前者如果记成功，就是把坏节点洗白。

**两种都不是证据**。所以现在遇到这类状态码，被动反馈**什么都不记**：不记成功、
不记失败，节点的 `FailureCount` 和熔断状态保持原样。

## 配置项

```
passive_ignore_status_codes = [403]
```

默认 `[403]`，可在线 PATCH 即时生效。显式传空数组 `[]` 表示关闭该规则，恢复
旧行为（任何完成的交换都记成功）。

## 为什么不是"一律判失败"

现网数据：近 3 小时 1592 条业务 403 中，能读出明文的全是请求特征类（10 条），
其余响应体是 gzip 原始字节读不出。**在看不见的情况下，一律判失败会大面积误杀**。

而"一律不记"没有这个风险：它只是拒绝让这次请求提供证据，节点原有的失败累计
不会因为一次 403 而被清零。要淘汰坏节点，靠的是探针和租约轮转——这两条路径
不受本次改动影响。

## 验证

本机 Docker 端到端，同一节点（`db4776cbe1bd003bf8f7b545d693e240`）：

| 步骤 | 操作 | failure_count | 结论 |
| --- | --- | --- | --- |
| 1 | 探针打不可达端口 ×2 | 2 | 失败正常累计 |
| 2 | 业务打 `/blocked` 得 403 | **2** | 403 不清零，未洗白 |
| 3 | 业务打 `/ok` 得 200 | 0 | 200 照常清零 |
| 4 | 再累计到 2，PATCH 空数组后打 403 | 0 | 规则可关闭，行为可回滚 |
| 5 | 恢复 `[403]`，累计到 2，再打 403 ×3 | **2** | 三次 403 均未改变计数 |

热更新验证：`passive_ignore_status_codes` 通过 `PATCH /api/v1/system/config`
即时生效，无需重启。

- `TestPassiveIgnoreStatusCodesEmptySlicePreserved` —— 显式空数组不被默认值覆盖

`go test ./...` 16 个包通过；`internal/proxy`（`wsarecv`）与 `internal/routing`
（纳秒断言）两条失败为改动前既有的 Windows 平台问题，与本改动无关。

## 已知边界

被动反馈只能覆盖**有流量的节点**。现网 3200+ 节点中绝大多数没有业务流量，本次
改动对它们没有影响——它们的健康状态仍由探针决定。要覆盖无流量节点，需要主动
探针携带完整客户端特征（v1.6.0 已具备该能力），这是下一步。
