# v1.5.0

## 探针新增「只判连通性」模式

上一版按状态码判节点，前提是探针请求能代表真实业务请求。实测发现这个前提在
OpenCode 免费层不成立：

- 探针目标 `https://api.opencode.ai` 不需要鉴权，好节点和坏节点都返回 200，
  状态码判定永远不触发。
- 换成真实业务端点后，不带凭据的请求一律返回
  `403 FreeTierError: can only be used from within OpenCode`。
- 关键是：**被上游封禁的出口返回的 403 与「没带身份」的 403 逐字节相同**
  （实测 5 个出口，响应体完全一致）。没有凭据就没有任何响应特征能区分二者。

结论是探针在没有凭据时无法判断节点好坏，硬按 403 判失败会误杀整个池子。

## 新增配置 `probe_reject_only_unreachable`

`PATCH /api/v1/system/config` 可写，默认 `false`（保持上一版行为）。

置为 `true` 后：

- 只有传输层失败（拨号超时、连接重置、TLS 错误）才计为探针失败；
- HTTP 交换一旦完成，无论状态码是 200、403、500，都算「可连通」；
- `probe_reject_status_codes` 与 `probe_reject_body_substrings` 在该模式下不生效；
- 探针脚本的 judge 也被跳过（脚本无法在无凭据时做出有效判断）。

这意味着该模式只能排除「完全连不上」的节点，无法排除「能连但被上游封禁」的节点。
后者需要凭据，见下。

## 验证

本机 Docker 端到端，四种情形：

- 严格模式 + 脚本判失败 → `failure_count` 0 → 1
- 连通性模式 + 同一判定 → `failure_count` 1 → 0
- 连通性模式 + 目标不可达 → `failure_count` 0 → 1（真断网仍会剔除）
- 连通性模式 + 可达但返回 500 → `failure_count` 保持 0

`go test ./...` 16 个包通过，两条既有失败与本次改动无关。

## 后续

要真正区分「能连但被封」的节点，探针必须携带真实凭据。需要在
`probe_request` 里配置真实的 `Authorization` 头，或给脚本注入凭据来源。
